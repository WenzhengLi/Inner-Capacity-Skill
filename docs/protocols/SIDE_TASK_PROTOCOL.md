# 支线任务协议

用途：把聊天中冒出来的想法、行动、实验和小研究登记成可追踪的支线任务。支线任务不是主线工作，也不是固定功能；它是用户成长过程中的临时抓手。

## 触发词

当用户说到以下词语时，进入支线任务判断：

- 登记任务
- 任务
- 支线任务
- 这个记一下
- 后面做
- 可以沉淀成一个任务

如果用户只是随口提到“任务”，先结合上下文判断。不要每次机械打断。

## 默认流程

1. 先复述理解：这件事可能是什么任务。
2. 问用户是否要登记为支线任务。
3. 如果用户确认，拆成任务标题、任务描述、下一步、验收方式。
4. 写入 `user-space/SIDE_TASKS.md`。
5. 如果任务来自聊天分析，把来源写为“聊天分析”。
6. 用户回答后，必须把用户回答、傻妞批改、阶段评分和下一步训练题写回任务详情。

## 拆分标准

一个合格支线任务至少包含：

- 为什么做：它解决什么成长、工作、关系、身体或认知问题。
- 做什么：具体动作，不写成空泛愿望。
- 怎么验收：用户如何知道它做完了。
- 下一步：最小可开始动作。
- 怎么批改：记录用户回答哪里对、哪里想简单了、可沉淀成什么模型。
- 怎么复盘：优先给用户一个具名历史人物和真实事件节点，让用户迁移应用；只有在用户明确要商业、工作或关系案例时，才使用类现实匿名场景。

## 任务粒度

支线任务要小，最好 1-7 天能推进一次。太大的想法要拆：

- 不要登记为“研究财富模型”。
- 可以登记为“画一张身边三个人的钱流图”。

## 与主线关系

支线任务不能吞掉主线。每次登记时都要标明：

- 是否影响工作主线。
- 是否影响身体底盘。
- 是否需要钱、时间、注意力投入。

如果支线任务有明显上头风险，应提醒用户先降规模。

## 批改记录

支线任务不是备忘录，必须有训练闭环。

用户每次回答后，任务详情里要补：

- 用户回答：尽量保留用户原意，压缩成条目。
- 傻妞批改：写清哪里对、哪里可能想简单了、需要补哪块。
- 阶段评分：0-100 分，只评估本次迁移掌握度，不评价人格。
- 下一步问题：一次只给 1-5 个问题，避免过载。

批改要直接，但不要为了尖锐而尖锐。优先抓最关键的 1-2 个点。

## 复盘训练

支线任务支持主动出题。用户可以说：

- 复盘这个任务
- 给我一个类似案例
- 出题
- 继续训练

此时输出一个具名历史人物和真实事件节点，并让用户回答。历史 / 处世 / 权力 / 用人类任务不要写成“一个年轻老板”“某家公司”这类匿名设定；要直接讲人物、时代、节点，顺便开展历史课。

复盘训练格式：

1. 人物小传：先大致介绍每个关键人物是谁、从哪里来、手里有什么资源、性格和风险是什么。
2. 历史背景：讲清朝代、局势、真实事件节点，篇幅可以接近一次“讲故事”的长度。
3. 关键矛盾：点出资源、约束、人物、风险，以及为什么这个局会变坏。
4. 用户作答：给 3-5 个开放问题。
5. 验收标准：说明答到什么算过关。

历史课式复盘题不能只写几句题干。用户需要先看懂“谁是谁、谁和谁什么关系、谁手里有什么、谁怕什么、谁能伤到根本”，再开始作答。

复盘训练可以用历史人物、商业案例、工作管理、亲密关系、身体自控、金钱风险等场景，但要围绕当前任务的训练目标。若任务本身是历史人物复盘，默认必须使用历史人物。

## 保存位置

模板见：

- `templates/user-space/SIDE_TASKS.md`

个人执行记录放在：

- `user-space/SIDE_TASKS.md`

## 输出格式

登记后简短输出：

```text
已登记支线任务：ST-YYYYMMDD-001
标题：...
下一步：...
验收：...
```

不要一次给用户塞很多任务。默认一次最多登记 3 个。
