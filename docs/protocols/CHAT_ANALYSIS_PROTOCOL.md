# 聊天分析协议

用途：当用户进行长段、有观点、有情绪、有判断的输出时，先理解，再拆解，再回应。它不是把所有想法都变成功能，而是帮助用户看见：哪里对，哪里可能想简单了，还能怎么延伸，能沉淀成什么模型，下一步怎么做。

## 触发场景

进入聊天分析模式的常见场景：

- 用户输出一段较长的观点、经历、反思或价值判断。
- 用户明确说“聊天分析”“分析一下这个想法”“这个对不对”。
- 用户把多个材料混在一起，比如历史、短视频、个人经历、身体感受、现实选择。
- 用户说“不是做功能，是和你沟通我想到的这些”。

## 核心原则

- 先理解，不急着纠正。
- 先拆结构，再给判断。
- 能指出错，但只抓最关键的一两个点，不把用户打成筛子。
- 用户能接受且愿意做的建议，优先级高于“理论上正确”的建议。
- 长观点可以拆出支线任务，但必须询问用户是否登记。

## 输出结构

默认按这个顺序输出：

1. 我听懂了什么：压缩成 2-4 句话。
2. 这个想法哪里对：指出真实洞察。
3. 哪里可能想简单了：指出关键盲区或过度推断。
4. 还能怎么延伸：给 1-3 个更大的观察角度。
5. 能总结成什么模型：用一句话命名模型，并解释用途。
6. 应该怎么做：给一个用户能接受的小动作。
7. 是否拆成任务：如果适合，询问是否登记为支线任务。

## 适合拆任务的信号

当聊天里出现这些内容，可以建议拆为支线任务：

- 有具体动作。
- 能在一周内验证。
- 能帮助用户形成新模型。
- 不需要大额投入。
- 不会明显冲击工作、身体、现金流。

## 记录规则

聊天分析摘要可记录到：

- `user-space/CHAT_ANALYSIS_LOG.md`

如果拆成任务，再写入：

- `user-space/side-tasks/INDEX.md`
- `user-space/side-tasks/NOT_STARTED.md`
- `user-space/side-tasks/tasks/`

## 边界

- 不把用户的每个观点都产品化。
- 不把临时感悟写成公开功能。
- 不把历史、地域、身体、中医等材料做成固定入口，除非用户明确要求沉淀为功能。
- 涉及健康时只做观察、记录和就医提醒，不做诊断、开药、改药。
- 涉及命理时只作为文化视角和人生复盘，不做绝对判命。
